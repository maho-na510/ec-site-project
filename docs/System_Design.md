# システム設計書

アーキテクチャの選定理由や設計方針についてまとめました。
「なぜそうしたのか」を中心に書いています。

---

## 全体構成

```
ブラウザ
  ↓
React（フロントエンド） :5173
  ↓ Viteのプロキシ経由
  ├─ /api/v1/*        → Rails API :3001   （ユーザー向け）
  └─ /api/admin/*     → Laravel API :8000 （管理者向け）
                              ↓
                         MySQL :3306   （データ保存）
                         Redis :6379   （セッション管理）
```

全部Dockerで動かしています。`docker compose up` で立ち上がるようにしました。

## アーキテクチャの選定理由

### なぜバックエンドを2つに分けたのか

課題の要件に「ユーザー側はRails、管理者側はLaravel」と書いてあったのでそうしました。
ただ、実際にやってみると「2つに分けることのメリット」も感じました。

- ユーザー側と管理者側でセキュリティの設定を完全に分けられる
- 片方が重くなっても、もう片方には影響しない
- 将来的に別チームで開発できる

デメリットとしては、同じDBを共有しているのでマイグレーションを両方で管理する必要があることです。
今回はRailsでマイグレーションを書いて、Laravelはそのテーブルを使う形にしました。

### なぜRailsをユーザー側にしたのか

Railsは「Convention over Configuration（設定より規約）」という考え方で、
決まったやり方で書けばコードが少なく済むと調べてわかりました。
ユーザー向け機能はCRUDが多いのでRailsが向いていると思いました。

### なぜLaravelを管理者側にしたのか

Laravelにはスケジューラーが標準で入っていて、`php artisan schedule:run` で
定期実行の処理が書きやすいと感じました。
今回の「毎日9時にCSV出力」という要件に合っていたので管理者側をLaravelにしました。

### なぜRedisをセッション管理に使ったのか

課題の要件に「セッションはファイルに保存しないでRedisに保存すること」と書いてあったためです。
調べたところ、Redisに保存するとサーバーを複数台に増やしたときでも
セッションが共有できるというメリットがあるとのことでした。

### なぜJWT認証にしたのか

最初はlocalStorageにトークンを保存して `Authorization: Bearer` ヘッダーで送る方式にしていました。
ところが調べると、localStorageはJavaScriptから読めるため、
XSS攻撃（悪意のあるスクリプトの挿入）でトークンが盗まれるリスクがあることがわかりました。

そこで **HttpOnly Cookie** に切り替えました。
HttpOnly Cookieはブラウザが自動で送信し、JavaScriptからは読み書きできません。
XSSでトークンを盗もうとしても `document.cookie` では取得できないため、より安全です。

管理者ログイン時に `admin_token` という名前のHttpOnly Cookieをセットし、
以降のリクエストはブラウザが自動でCookieを送信します。
ログアウト時は同じCookieを `Max-Age=-1` で上書きして無効化しています。

## 設計方針

### サービス層を作った理由

コントローラーに全部書くと長くなるし、テストしにくいと感じたので
`app/services/` にビジネスロジックを切り出しました。

例えば注文処理は `OrderProcessingService` という別クラスにまとめています。
コントローラーはリクエストを受け取って結果を返すだけ、という役割にしました。
これを「単一責務の原則」というらしいです（SOLIDのSに当たる部分）。

### 在庫の同時購入問題への対応

同じ商品を2人が同時に購入した場合、在庫がマイナスになってしまう問題があります。
調べたところ「悲観的ロック（SELECT FOR UPDATE）」で解決できると分かりました。

```ruby
# トランザクション内で行をロックする
Product.lock('FOR UPDATE').find(product_id)
```

さらに念のため、SQLの更新文でも在庫チェックを入れています。

```sql
UPDATE products
SET stock_quantity = stock_quantity - 数量
WHERE id = ? AND stock_quantity >= 数量
```

更新された行数が0だったら在庫切れとして処理します。
2重に確認することで、万が一の場合にも対応できるようにしました。

### パフォーマンスへの配慮

いくつか意識したことがあります。

**N+1問題の対策**

RailsのActiveRecordで `includes` を使ってN+1を防いでいます。

```ruby
# 商品一覧を取得するとき、カテゴリと画像も一緒に取得する
products = Product.includes(:category, :product_images)
```

最初は `includes` を書き忘れてSQLが大量に発行されていて、
Rails の developmentログを見て気づきました。

**TanStack Queryのキャッシュ**

フロントエンドではTanStack Query（React Query）を使っています。
一度取得したデータは5分間キャッシュされるので、
同じデータを何度もAPIから取得しなくて済みます。

**DBのインデックス**

よく検索・絞り込みに使うカラムにはインデックスを貼っています。
`products.is_active`、`products.category_id`、`orders.user_id` などです。

## セキュリティについて

**APIへのアクセス制御**

管理者向けAPIには `auth:api` ミドルウェアを使って、
JWTトークンがないとアクセスできないようにしています。

**CORS設定**

APIサーバーはフロントエンドのURLからのリクエストしか受け付けないよう設定しています。

**SQLインジェクション対策**

RailsのActiveRecordやLaravelのEloquentを使っているので、
クエリはプリペアドステートメントで実行されます。
ただ、在庫のアトミック更新でSQL文字列を組み立てている部分は
`to_i` で整数に変換してから埋め込むようにしました。

**パスワード**

Railsでは `has_secure_password` を使っています。
パスワードはbcryptでハッシュ化されてDBに保存されます。

## 工夫したところ

**フロントエンドのAPIクライアント**

RailsのレスポンスはAPIが `snake_case`（例：`created_at`）で返しますが、
JavaScriptでは `camelCase`（例：`createdAt`）が一般的です。
`api.ts` でレスポンスを自動変換する処理を書いたので、
各ページでいちいち変換しなくてよくなりました。

**コントローラーのシンプルさ**

コントローラーはできるだけ薄く、サービス層に処理を任せる設計にしました。
おかげでコントローラーのテストが書きやすくなったと思います。

**管理者専用ルートのガード**

フロントエンドで `AdminRoute` というコンポーネントを作って、
管理者以外が `/admin/*` にアクセスしたら自動でリダイレクトするようにしました。

## つまずいた点と学んだこと

### HttpOnly Cookie に切り替えてテストが書けなくなった

JWTをlocalStorageからHttpOnly CookieにするとJavaScriptから読めないので、
テストでトークンを取り出してリクエストに付けることができなくなりました。

調べたところ、テストでは `JWTAuth::fromUser($admin)` でトークンを直接生成して
`Authorization: Bearer` ヘッダーに付ける方法があることがわかりました。
本番の認証フロー（Cookieを使う）とは別ルートですが、テスト環境では有効な方法でした。

### N+1問題に気づかなかった

商品一覧ページを開いたときに、Railsのdevelopmentログを見ていたら
SQLが何十回も発行されていることに気づきました。
商品ごとにカテゴリを取りに行くSQLが出ていて、これが「N+1問題」というものと知りました。
`includes` を使えば一発で解消できたので、そこからは意識して書くようにしました。

### カートの設計でテーブルを2つに分けるか迷った

カートを `carts` と `cart_items` に分けるか、`cart_items` だけにするか迷いました。
最終的に `carts` テーブルを作ったのは「チェックアウト済みかどうか」を
`checked_out_at` で管理して注文履歴として残せるようにしたかったからです。
1つのテーブルにまとめると `user_id` に対して「現在のカート」を特定するロジックが複雑になりそうだったので分けました。

### RailsとLaravelでマイグレーションを共有する問題

2つのフレームワークが同じDBを使うので、マイグレーションが二重管理になる問題がありました。
今回はRailsでメインのマイグレーションを書いて、Laravelはそのテーブルを使う方針にしました。
ただしLaravel固有のカラム（`created_by_admin_id` など）はLaravel側のマイグレーションで追加しています。

## 使用技術と選定理由まとめ

| 技術 | 理由 |
|---|---|
| React | コンポーネントで画面を作りやすく、状態管理もしやすい |
| Rails | 規約に従えば素早く実装できる。ActiveRecordが便利 |
| Laravel | スケジューラーが使いやすい。PHP Unitでテストが書きやすい |
| MySQL | 一般的なRDB。Rails・Laravelのどちらからも使える |
| Redis | セッションの保存。ファイル保存より速い |
| Docker | 環境の差異をなくして、誰でも同じ環境で動かせる |
| Tailwind CSS | クラス名を書くだけでスタイルが当たるので作業が速い |
| JWT | フロントエンドとのAPI通信に向いている |
| TanStack Query | APIのキャッシュと状態管理が楽になる |
